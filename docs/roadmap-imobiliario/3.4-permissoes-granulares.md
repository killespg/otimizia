# 3.4 — Permissões granulares e governança

Item de Fase 3 (esforço G, compromisso original, **mudança sensível**).
Depende de 0.3 (matriz e testes de RLS já aprovados). Rollout: "por flag,
organização a organização, nunca big-bang" — texto do próprio roadmap
para este item, seguido à risca na implementação.

## O problema real (documentado em 0.3, resolvido aqui)

A matriz de 0.3 (`docs/roadmap-imobiliario/0.3-fundacao-seguranca-rollout.md`)
já apontava: fora do vertical imobiliário, **qualquer membro da
organização, com qualquer `job_role`, tem acesso total de leitura e
escrita** a `contacts`/`deals`/`tasks`. Esse é o gap que este item fecha
— mas com uma estratégia de rollout que garante zero regressão em toda
organização que não optar por ativar.

## Como a estratégia de zero-regressão funciona

RLS do Postgres combina múltiplas policies com **OR entre permissive** e
**AND entre restrictive**. As policies existentes
(`contacts_all_org`/`deals_all_org`/`tasks_all_org`, de
`0020_org_rls.sql`) são permissivas e continuam exatamente como estão.

Este item **não mexe nelas** — adiciona policies **restrictive** novas
(`*_manage_scope_update`/`*_manage_scope_delete`) que só entram em vigor
quando a organização tem `organizations.granular_rbac_enabled = true`. A
função `can_manage_crm_resource()` que essas policies chamam começa com
`not granular_rbac_enabled or ...` — ou seja, **enquanto o flag estiver
desligado (o padrão de toda organização hoje), a restrictive policy é
sempre verdadeira e nunca bloqueia nada**. Isso não é "quase" seguro
contra regressão — é estruturalmente impossível a mudança afetar uma
organização que não ativou o flag, mesmo que haja um bug na lógica de
escopo, porque o curto-circuito do flag desligado nem chega a avaliar o
resto da condição no caminho comum.

Sem policy de `UPDATE` pra `authenticated` em `organizations.granular_rbac_enabled`
— mesmo padrão de `real_estate_v2_enabled` (0057): só a operação (service
role) liga o flag, organização por organização, depois de validar. Não
existe toggle de auto-serviço na UI.

## O modelo de permissão (v1)

- **Ver**: continua liberado pra todo membro, com ou sem o flag. O
  roadmap pede escopo em "gerenciar" (editar/excluir), não em "ver".
- **Gerenciar** (`update`/`delete`) em `contacts`/`deals`/`tasks`, com o
  flag ligado:
  - Admin da organização: sempre pode.
  - `job_role` em `owner`/`broker`/`agent`/`managing_partner`/`lawyer`:
    gerencia qualquer registro (mesmos cargos "de gestão" já usados nas
    funções `can_manage_realestate`/`can_manage_legal`).
  - Qualquer outro `job_role` (`assistant`, `staff`, `intern`,
    `receptionist`, `finance`, `paralegal`): só gerencia registros onde é
    o `assignee_id` ou o `owner_id` — **escopo próprio**.
- **Escopo "equipe"** (delegar por time/departamento, mencionado no
  roadmap) **não foi implementado** — o schema atual não tem conceito de
  time dentro da organização. Fica como extensão futura.
- `lib/permissions.ts` é a fonte de verdade em TypeScript
  (`canManageCrmResource`, testado em `lib/permissions.test.ts`, 6 casos)
  e espelha exatamente a função SQL `can_manage_crm_resource()` —
  mesma convenção de manter duas fontes em sincronia manual já usada
  entre `lib/real-estate.ts` e as funções SQL de 0051.

## O que fica de fora, de propósito

- **Nenhuma UI usa `lib/permissions.ts` ainda** — esta entrega é
  fundação de banco + lógica pura testada, não uma mudança de interface.
  Botões de editar/excluir continuam aparecendo pra todo mundo
  independente do RBAC granular; esconder ações que o backend já bloqueia
  é refinamento de UX de uma próxima iteração.
- **Sem UI de toggle** — ativar o flag é manual, via service role,
  intencionalmente (ver acima).
- **Campos sensíveis** (mascarar valor de negócio, comissão etc. por
  cargo) — mencionado no roadmap ("campos sensíveis"), não coberto aqui.
  RLS do Postgres restringe linha, não coluna; mascarar campo por papel
  exigiria mudar o que cada `select` devolve, não só policies.

## Verificação

- `npm run test` (195 testes, 6 novos em `lib/permissions.test.ts`),
  `npx tsc --noEmit`, `npm run lint` e `npm run build` sem erros.
- `test/integration/rls.test.ts`, bloco
  `describe("RBAC granular por flag (3.4)", ...)`: com o flag desligado,
  `staff` continua editando negócio de outro dono (comportamento
  inalterado); com o flag ligado, `staff` só edita o próprio, `broker`
  continua editando qualquer um, e visualização continua liberada pra
  todo mundo.
- **Mesma limitação de sempre**: sem Docker/Supabase local para rodar
  contra Postgres de verdade — a garantia estrutural do "flag desligado
  nunca bloqueia" descrita acima é sólida por como RLS restrictive
  funciona, mas o teste que prova isso na prática precisa rodar contra
  uma instância real antes de qualquer organização ativar o flag.
