# 3.2 — Construtor de automações

Item de Fase 3 (esforço G, evolução do compromisso). Depende de 3.1 — só
faz sentido construir uma UI de regras depois que o motor genérico existe.

## O que foi entregue

- `app/(app)/settings/automation-actions.ts`: `createAutomationRule()`,
  `toggleAutomationRule()`, `deleteAutomationRule()` — admin-only (mesma
  régua de `/settings/integracoes`, 2.4).
- `app/(app)/settings/automacoes/page.tsx`: formulário guiado — escolhe
  gatilho (`deal_created`/`deal_stage_changed`/`deal_inactive`), escopo
  opcional de pipeline/etapa, ação (`create_task`/`send_email`/`change_stage`)
  e os parâmetros da ação (templates de título/assunto/corpo, ou etapa de
  destino). Lista as regras existentes com ativar/desativar/excluir, e
  mostra as últimas 20 linhas de `automation_executions` como histórico.
- Link a partir de Configurações (`/settings`), no mesmo padrão de
  Integrações.

## Onde este item fica claramente aquém do que o roadmap pede

O roadmap descreve "editor guiado com validação, **simulação em dados
passados**, **versão** e **histórico**". O que foi entregue:

- ✅ Editor guiado (formulário com os campos certos por tipo de gatilho/ação).
- ✅ Validação (server action rejeita gatilho/ação/etapa inválidos).
- ✅ Histórico (últimas execuções, via `automation_executions` — já existia
  da 3.1, só exposto na UI aqui).
- ❌ **Simulação contra dados passados** — não implementada. Rodar a regra
  contra os últimos N negócios reais antes de ativar de verdade seria o
  jeito de "criar regras úteis sem suporte e sem aumento de incidentes"
  (porta de saída do item) — sem isso, o primeiro teste de uma regula é em
  produção.
- ❌ **Versionamento** — editar uma regra hoje significa excluir e criar de
  novo; não há histórico de mudanças nem capacidade de reverter pra uma
  versão anterior.

Essas duas lacunas são as que mais interessam pro DoD do item ("usuários
criam regras úteis sem suporte e sem aumento de incidentes") — sem
simulação, o risco de uma regra mal configurada (principalmente
`change_stage`, já sinalizado como a ação mais arriscada em 3.1) só aparece
depois que ela já rodou de verdade.

## Formulário sem campos condicionais dinâmicos

Os campos de parâmetro de ação (título de tarefa, assunto/corpo de
e-mail, etapa de destino) aparecem todos juntos, com uma nota pedindo pra
preencher só o que é relevante pra ação escolhida — não há JavaScript de
cliente escondendo os campos que não se aplicam. Ficou assim para manter a
página inteiramente server-rendered (sem componente cliente novo); esconder
campos dinamicamente por tipo de ação é uma melhoria de UX de baixo risco
pra uma próxima iteração, não bloqueante.
