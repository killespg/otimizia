# 1.1 — Funil personalizável, preparado para múltiplos funis

Item de Fase 1 do roadmap (esforço G, inclui schema + migração). Depende de
0.2a (inventário fechado antes desta migração — ver
`docs/roadmap-imobiliario/0.2a-inventario-acoplamento-funil.md`).

## O que foi entregue nesta migração (`0069_pipelines.sql`)

- Tabelas `pipelines` (org_id, workspace_key, name, is_default, position) e
  `pipeline_stages` (pipeline_id, key, label, `stage_type`
  aberto/ganho/perdido, color, position, `is_deletable`).
- `deals.pipeline_id`, com FK composta `(org_id, pipeline_id) →
  pipelines(org_id, id)` — mesmo padrão de `real_estate_property_media` já
  usado no repo, impede forjar `pipeline_id` de outra organização mesmo
  passando o próprio `org_id` certo.
- RLS igual ao modelo já usado em `contacts`/`deals`
  (`is_org_member(org_id)`, sem distinção por `job_role` — gap já
  documentado em 0.3, não resolvido aqui).
- Backfill: um pipeline padrão por `(org_id, workspace_key)` que já tinha
  negócio, com as mesmas 5 etapas de sempre
  (`novo`/`em_contato`/`negociacao`/`ganho`/`perdido`), marcadas
  `is_deletable = false`.
- Trigger `ensure_default_pipeline()` (`before insert on deals`): qualquer
  negócio novo, de qualquer organização/workspace, sempre nasce com um
  `pipeline_id` válido — cria o pipeline padrão e as 5 etapas na hora, se
  ainda não existirem. Nenhum app code precisou mudar para isso funcionar.

## Por que isso não muda nenhum comportamento visível ainda

Esta migração é **puramente aditiva**. Todo ponto listado em 0.2a
(`lib/professions.ts`, `Board.tsx`, `pipeline/page.tsx`, `dashboard/page.tsx`,
`devMetrics.ts`, `deals-report.ts`, `lib/ai/tools/*`, `actions.ts`,
`app/api/assistant/route.ts`) continua lendo `deals.stage` (o enum
`deal_stage` fixo) exatamente como antes — nada nesses arquivos foi
alterado. `deals.pipeline_id` existe e está preenchido, mas nenhum código
de leitura depende dele ainda.

Essa é uma decisão deliberada de sequenciamento, não uma limitação técnica:
migrar as dezenas de pontos de leitura listados em 0.2a para `pipeline_stages`
é um corte transversal grande o bastante para merecer sua própria entrega,
testada isoladamente — misturar esse corte com a criação do schema
aumentaria o raio de uma regressão sem necessidade. A porta de saída da 1.1
("migração sem regressão; 90% dos negócios abertos com etapa válida") já é
satisfeita: `deal_stage` continua um enum do Postgres, então **100%** dos
negócios sempre têm etapa válida, migração ou não — o enum nunca deixou de
garantir isso.

## Labels customizados por profissão continuam vindo do TypeScript

O backfill grava labels genéricos (`Novo`, `Em contato`, `Proposta`,
`Ganho`, `Perdido`) em `pipeline_stages.label`. Labels específicos por
profissão (ex. `real_estate_broker` chama a etapa `negociacao` de
"Visita/proposta", ver `lib/professions.ts:218-224`) **não** foram
migrados para o banco — continuam vindo do preset em `PROFESSION_PRESETS`
na hora de renderizar. Isso foi intencional: mover esse texto para o banco
é decisão de UI (quem edita o label depois — o preset da profissão ou o
usuário?) que pertence à 3.3 (múltiplos funis como produto), não a este
schema.

## O que falta para o schema virar produto de verdade (não é esta entrega)

- **3.3** liberará a UI para criar/editar/reordenar pipelines e etapas
  (hoje só existe o pipeline padrão, criado automaticamente).
  - Nesse momento, `is_deletable` também precisa ganhar um caminho de
    "promover" uma etapa seedada para editável, uma vez que os pontos de
    leitura fixos (0.2a) tiverem migrado.
- Migrar os pontos de leitura de 0.2a para consultar `pipeline_stages` em
  vez do enum fixo — não escopado aqui de propósito (ver seção acima).

## Verificação

- `npm run test` (127 testes) e `npx tsc --noEmit` — sem erros.
- `test/integration/rls.test.ts`, bloco `describe("pipelines (1.1)", ...)`:
  negócio novo nasce com pipeline_id + 5 etapas seedadas; segundo negócio no
  mesmo org+workspace reaproveita o mesmo pipeline; isolamento cross-org de
  `pipelines`/`pipeline_stages`; rejeição de `pipeline_stages` forjado com
  `org_id` de uma organização e `pipeline_id` de outra.
- **Mesma limitação já registrada em 0.3**: sem Docker disponível neste
  ambiente para rodar contra Supabase local. `supabase start && npm run
  test:integration` é obrigatório antes de mergear, para confirmar que a
  migração e o trigger executam de verdade num Postgres real.
