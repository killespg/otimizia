# 3.1 — Motor de regras v1

Item de Fase 3 (esforço G, evolução do compromisso). Depende de 1.4 — o
follow-up por inatividade é o primeiro caso de uso real do motor, e seus
eventos já seguiam um contrato genérico o bastante pra migrar sem
mudar comportamento.

## O que foi entregue

- `supabase/migrations/0075_automation_engine.sql`:
  - `automation_rules`: `trigger_kind` (`deal_created` / `deal_stage_changed`
    / `deal_inactive`), `trigger_params` (jsonb — hoje só
    `inactivity_days` pro gatilho de inatividade), coringa de
    `pipeline_id`/`stage_key` (mesmo padrão de `deal_followup_rules`),
    `action_type` (`create_task` / `send_email` / `change_stage`) e
    `action_params` (templates).
  - `automation_executions`: log de cada execução (sucesso/falha/pulado),
    com índice único `(rule_id, event_id)` — dedupe de banco pros gatilhos
    de evento discreto. `deal_inactive` não tem `event_id` (é checado por
    polling, não por evento), então seu dedupe continua sendo "já existe
    tarefa aberta", igual à 1.4.
  - Migra os dados de `deal_followup_rules` para `automation_rules`
    (`trigger_kind = 'deal_inactive'`) e **derruba a tabela antiga**. Isso
    só foi seguro porque `deal_followup_rules` nunca chegou a rodar em
    produção — nasceu nesta mesma leva de entregas. Não é o padrão para
    migrações que tocam dado real de cliente.
  - `tasks.source` ganha `'automation_rule'` como valor permitido (mantém
    `'followup_rule'` por segurança, mesmo sem uso esperado daqui pra
    frente).
- `lib/automation-template.ts`: `renderTemplate()` (substituição
  `{{caminho.aninhado}}`, sem lógica condicional — o suficiente pros
  templates do v1) e `matchesEventRuleScope()` (mesmo coringa de
  pipeline/etapa de 1.4, aplicado a gatilhos de evento). Testado em
  `lib/automation-template.test.ts` (8 casos).
- `lib/followup.ts` **não mudou** — `matchRule()`/`computeFollowupCandidates()`
  são genéricos o bastante pra continuar sendo a lógica de avaliação do
  gatilho `deal_inactive` dentro do motor novo, sem duplicar código.
- `app/api/cron/automation-engine/route.ts` **substitui**
  `app/api/cron/followup-rules` (removido). Duas fases:
  - **Fase A (evento discreto)**: lê `crm_domain_events` do tipo
    `deal.created`/`deal.stage_changed` ainda não processados (mesmo
    `processed_at` que a 2.4 já usa pra outros consumidores), casa contra
    `automation_rules` ativas do tipo certo, executa a ação.
  - **Fase B (inatividade, polling)**: mesma lógica que existia no cron de
    1.4, agora lendo de `automation_rules` em vez de
    `deal_followup_rules`.
  - As três ações (`create_task`, `send_email`, `change_stage`) são
    despachadas por um `executeAction()` só, cada uma logada em
    `automation_executions`.

## Ações — o que cada uma faz e o que fica de fora

- **`create_task`**: igual ao comportamento antigo da 1.4, só que também
  disponível pra gatilhos de evento (não só inatividade).
- **`send_email`**: reaproveita `sendEmail`/`contactMessageEmail` (2.1) e
  respeita `email_opt_out`. Se o negócio não tem contato com e-mail, a
  execução é `skipped` (não `failed`) — não é erro, é a regra não se
  aplicar a este negócio.
- **`change_stage`**: só aceita uma das 5 etapas fixas do enum
  `deal_stage` (validado antes do update, além da validação do próprio
  enum no banco). **Mover automaticamente a etapa de um negócio é a ação
  de maior risco das três** — uma regra mal configurada pode empurrar
  negócios pra "ganho"/"perdido" sem intervenção humana. Não há proteção
  extra além da validação de etapa nesta entrega (ex: não pede
  confirmação, não tem limite de quantos negócios por execução) —
  documentado como risco conhecido, não mitigado ainda.

## O que fica de fora, de propósito

- **Sem UI de criar regra** — a tabela e o motor existem, mas criar uma
  regra hoje é via SQL direto (mesma situação de `deal_followup_rules`
  antes desta entrega). Isso é o item **3.2** (construtor de automações),
  que o próprio roadmap já lista como dependente da 3.1 rodando primeiro.
- **Sem dry-run nem simulação contra dados passados** — pedido pelo
  roadmap ("templates prontos, dry-run"), não implementado. Só dá pra
  testar criando uma regra de verdade e observando `automation_executions`.
- **Sem limite de execuções por regra/janela de tempo** — uma regra mal
  configurada (ex: `change_stage` num gatilho muito amplo) pode executar
  em muitos negócios de uma vez, sem circuit breaker.
- **Cron não agendado em `vercel.json`** — mesmo racional dos outros crons
  desta leva: sem UI de criar regra, não há regra real pra processar
  ainda.

## Verificação

- `npm run test` (189 testes, 8 novos em `lib/automation-template.test.ts`),
  `npx tsc --noEmit`, `npm run lint` e `npm run build` sem erros
  (`/api/cron/automation-engine` aparece na build; `/api/cron/followup-rules`
  não existe mais).
- `test/integration/rls.test.ts`, bloco
  `describe("automation_rules e automation_executions (3.1)", ...)`:
  isolamento cross-org, só admin lê `automation_executions`, e a trigger
  de `deals` emite `deal.stage_changed` corretamente (a execução do cron
  em si não é testada aqui — precisa do servidor rodando).
- **Mesma limitação de sempre**: sem Docker/Supabase local para validar a
  migração de dados e as triggers de ponta a ponta, e sem ambiente real
  pra rodar o cron manualmente contra uma regra de verdade.
