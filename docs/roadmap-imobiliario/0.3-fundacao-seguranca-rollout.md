# 0.3 — Fundação de segurança e rollout

Item de Fase 0 do roadmap do CRM imobiliário (v6), pré-requisito de
segurança. A classe de bug priorizada aqui é **vazamento de dado entre
corretores da mesma equipe** (mesma organização, papel diferente), não um
bug visual — e isso não muda nenhuma permissão hoje, só torna o estado atual
auditável e testado. Mudar permissões de verdade é o item 3.4 (Fase 3).

## Matriz cargo × recurso × ação (estado atual, não o estado desejado)

Os papéis reais em `organization_members.job_role` são `owner`,
`managing_partner`, `lawyer`, `paralegal`, `finance`, `receptionist`,
`intern`, `staff`, `broker`, `agent`, `assistant` (ver
`supabase/migrations/0051_real_estate_job_roles.sql`). O papel amplo de
organização (`organization_members.role`) é só `admin` ou `member`.

| Recurso | Papel de org (`role`) | `job_role` | Ver | Gerenciar (criar/editar/excluir) |
|---|---|---|---|---|
| `contacts`, `deals`, `tasks`, `interactions` (CRM core) | `admin` ou `member` | qualquer | ✅ todo membro da org | ✅ todo membro da org — **não há distinção por `job_role` hoje** |
| `real_estate_properties` e tabelas relacionadas (0052+) | `admin` ou `member` | `owner`/`broker`/`agent`/`assistant` | ✅ | `owner`/`broker`/`agent` gerenciam; `assistant` só lê (`can_view_realestate`/`can_manage_realestate`, 0051) |
| `real_estate_properties` (mesmo recurso) | `admin` ou `member` | `staff`, `intern`, etc. (papéis não-imobiliários) | ❌ | ❌ — fora da lista de `can_view_realestate` |
| `real_estate_commissions`, `real_estate_targets` | isolamento por `org_id` (RLS) | qualquer membro da org | ✅ | ✅ — **mesmo gap**: sem distinção por `job_role` |
| `organizations` (config, billing) | só `admin` edita | — | ✅ membros leem | ✅ só `admin` |
| `organization_members` (papéis) | só `admin` gerencia | — | ✅ membros leem | ✅ só `admin` — agora **auditado** (ver abaixo) |
| `audit_log` (novo, esta entrega) | só `admin` lê | — | ✅ só `admin` | ❌ ninguém escreve por fora do trigger |

**Leitura da matriz**: fora do vertical imobiliário
(`real_estate_properties` e afins), **qualquer membro da organização — não
importa o `job_role` — tem acesso total de leitura e escrita** a contatos,
negócios, tarefas e interações. Isso é esperado hoje (é o modelo "RLS por
organização" de `0020_org_rls.sql`, pensado para equipes pequenas e
confiança entre membros) e é exatamente o gap que o item 3.4 (RBAC
granular, Fase 3) resolve depois — não é bug, é escopo ainda não
implementado. Esta entrega não muda isso; só deixa o comportamento atual
testado e o log de mudança de papel auditável.

## Testes negativos adicionados

`test/integration/rls.test.ts`, bloco `describe("audit_log (0.3)", ...)`:

- Entrada de auditoria criada em `member_added`, `member_role_changed`
  (com `before`/`after`) e `member_removed`.
- Um `UPDATE` que não muda `role` nem `job_role` (ex. só `created_at`) não
  gera entrada — evita ruído no log.
- Membro comum (não-admin) não lê nenhuma linha do `audit_log` da própria
  organização; admin lê.
- Nenhum client autenticado consegue `insert`/`update`/`delete` diretamente
  em `audit_log` — só o trigger (via função `security definer`) escreve.

Os testes já existentes de `job_role=assistant` vs `job_role=agent` em
`real_estate_properties` (linha ~217) continuam cobrindo a única
diferenciação por `job_role` que já existe no código hoje.

**Limitação conhecida**: esta suíte só roda contra Supabase local
(`describe.skipIf(!config)`, ver `test/integration/helpers.ts`). Neste
ambiente de execução não havia Docker disponível para subir uma instância
local — os testes foram revisados e o arquivo foi validado por
`tsc --noEmit` e coleta do Vitest (30 testes coletados, todos "skipped" sem
Supabase local, nenhum erro de sintaxe/import). Rodar
`supabase start && npm run test:integration` antes de mergear é obrigatório
para confirmar que a migração executa e os testes passam de verdade.

## Feature flags e rollout

Não foi criada uma infraestrutura de flag genérica nova. O padrão já
existente no código é reaproveitado como o mecanismo oficial de rollout
gradual: uma coluna booleana por organização (ver
`supabase/migrations/0057_real_estate_v2_feature_flag.sql` e
`lib/real-estate.ts:isRealEstateV2Enabled`) — sem policy de `UPDATE` para
`authenticated`, então só a operação (service role/admin) liga uma
organização por vez. Qualquer feature sensível nova (ex. 3.4 RBAC granular)
deve seguir o mesmo padrão: `org.<feature>_enabled boolean not null default
false`, ligado org a org, nunca big-bang — é literalmente o que o roadmap
pede na seção "Rollout" do item 3.4.

## Runbook de rollback

Para qualquer entrega que siga o padrão de flag acima:

1. **Desligar sem deploy**: `update organizations set <feature>_enabled =
   false where id = '<org_id>'` via service role — reverte o rollout para
   aquela organização imediatamente, sem migração nem redeploy.
2. **Reverter a migração**, se o problema for de schema: toda migração
   neste roadmap é escrita para ser reversível com uma migração nova (não
   editando a antiga) — ex. para esta entrega,
   `drop trigger if exists organization_members_audit on public.organization_members;`
   `drop function if exists public.log_organization_member_change();`
   `drop table if exists public.audit_log;`.
3. **Confirmar isolamento**: depois de qualquer rollback, rodar
   `npm run test:integration` contra o Supabase local/staging antes de
   liberar de novo — é o mesmo comando que valida RLS hoje.
4. **Auditoria pós-incidente**: qualquer suspeita de vazamento cross-org ou
   entre papéis agora tem uma primeira fonte de verdade —
   `select * from audit_log where org_id = '<org_id>' order by created_at
   desc` (só executável como `admin` da própria org, ou via service role
   pela operação).
