# 5.3 — Marketplace de automações e playbooks

Esforço G, Fase 5. Depende de 3.1/3.2 (motor de regras e construtor de
automações), já em produção.

## O que foi entregue

Uma galeria de 3 modelos prontos em
`app/(app)/settings/automacoes/page.tsx` (`AUTOMATION_TEMPLATES`),
inserida acima do formulário "Nova regra" existente:

1. **Follow-up de 5 dias sem contato** — `deal_inactive` (5 dias) →
   `create_task` ("Retomar contato — {{deal.title}}").
2. **Comemorar fechamento** — `deal_stage_changed` (etapa `ganho`) →
   `create_task` ("Pedir indicação — {{deal.title}}").
3. **E-mail de boas-vindas ao criar negócio** — `deal_created` →
   `send_email` (assunto/corpo prontos).

Cada card mostra nome, descrição em linguagem natural e um resumo
"gatilho → ação" antes de instalar — a "prévia legível da configuração"
pedida na porta de saída do item.

## Decisões de design

- **Modelos versionados em código, não em tabela.** Ainda não existe
  necessidade de curadoria dinâmica (adicionar/remover modelo sem deploy)
  nem modelos de terceiros — só 3 modelos internos. Uma tabela
  `automation_templates` seria complexidade prematura para 3 linhas
  fixas; se o catálogo crescer ou precisar ser editado por não-devs, aí
  sim vale migrar para dados.
- **"Instalar" reaproveita `createAutomationRule` sem nenhuma mutação
  nova.** O formulário de cada card é o mesmo `<form action=
  {createAutomationRule}>` do construtor manual (3.2), só com os campos
  pré-preenchidos via `<input type="hidden">`. Depois de instalado, o
  modelo vira uma regra comum na lista "Regras ativas" — pode ser
  editado, ativado/desativado ou excluído com os controles que já
  existiam antes deste item, sem nenhum código de "desinstalar"
  especial.
- **Sem versionamento de modelo instalado.** Se o código do modelo mudar
  no futuro, regras já instaladas não são atualizadas retroativamente —
  são cópias independentes no momento da instalação, assim como preencher
  o formulário manual sempre foi. Isso é consistente com como
  `automation_rules` já funciona, não uma limitação nova deste item.
- **"Playbooks" (sequências de múltiplas regras) não foram
  implementados.** O roadmap menciona "automações e playbooks" — cada
  modelo aqui é uma única regra, não uma sequência orquestrada de
  vários passos. Um playbook de verdade (ex: "sequência de 3 e-mails ao
  longo de 2 semanas") exigiria um conceito novo de estado/agendamento
  que o motor de regras (3.1) não tem hoje — não é gap deste item
  especificamente, é limitação do motor subjacente.

## Verificação

- `npx tsc --noEmit`, `npm run lint`, `npm run build` sem erros.
- `npm run test` — sem novos testes unitários porque não há lógica pura
  nova (a galeria é só dados estáticos + reaproveitamento de uma server
  action já testada indiretamente pela cobertura de 3.2).
- **Mesma limitação de sempre**: sem navegador autenticado disponível
  nesta sessão para clicar "Instalar" e confirmar visualmente que a
  regra aparece correta em "Regras ativas" — recomenda-se essa checagem
  manual antes de mesclar.
