# 4.5 — Tendências e inteligência de portfólio

Último item de Fase 4 (esforço G, compromisso original). Depende de 1.5
(infraestrutura de relatório) e 2.3 (dados limpos).

## O que foi entregue

- `lib/real-estate-trends.ts`:
  - `computeDemandByNeighborhood()`/`computeDemandByPropertyType()` —
    agrupa `real_estate_lead_preferences` (o que os clientes pedem) por
    bairro/tipo.
  - `computeVelocityByType()` — dias médios entre criação e fechamento
    (vendido/alugado) por tipo de imóvel.
  - `computePortfolioGaps()` — cruza demanda declarada com o que a
    carteira tem, mostrando onde falta estoque.
  - **Toda função devolve `sufficientSample`** — a porta de saída do item
    exige "regras de mínimo amostral, intervalos de confiança e feedback
    provam utilidade antes de qualquer previsão avançada"; `MIN_SAMPLE_SIZE`
    (5) é o mínimo abaixo do qual um número vem marcado como amostra
    insuficiente, mas **nunca escondido** — mostrar "n=2, amostra
    insuficiente" é mais honesto que omitir ou, pior, mostrar como se
    fosse confiável.
  - Testado em `lib/real-estate-trends.test.ts` (7 casos).
- `app/(app)/imoveis/tendencias/page.tsx`: quatro seções (demanda por
  bairro, demanda por tipo, velocidade por tipo, lacunas de estoque),
  cada uma sinalizando visualmente quando a amostra é insuficiente. Atrás
  do mesmo gate de `real_estate_v2_enabled` + `canViewRealEstate` do
  dashboard imobiliário (RE-6xx).

## "Perfil provável" (o antigo "perfil do cliente ideal a partir do
portfólio") — não implementado

O roadmap menciona explicitamente que este item "inclui o antigo 'perfil
do cliente ideal a partir do portfólio'". Isso é o inverso do matching
(4.1): em vez de "que imóvel serve este cliente", seria "que tipo de
cliente esse portfólio atrai". Não foi implementado nesta entrega —
sobrepõe-se com o "caminho inverso portfólio → perfil provável" já citado
como gap em 4.1
(`docs/roadmap-imobiliario/4.1-matching-v2.md`), e resolver os dois
juntos evita duplicar a mesma lógica de inferência de perfil em dois
lugares.

## Velocidade — limitação real, não só nota

`computeVelocityByType()` usa `updated_at` do imóvel como proxy de "quando
fechou" (mudou pra vendido/alugado). **Não existe uma coluna dedicada de
data de fechamento** — se o corretor editar qualquer outro campo do imóvel
depois de marcá-lo como vendido, `updated_at` avança e a velocidade
calculada fica errada. Mesma classe de limitação já documentada em 1.5
("dias em aberto" usa `created_at` como proxy, não histórico real de
mudança de etapa). Resolver isso de verdade exige uma coluna
`sold_at`/`rented_at` própria, preenchida no momento exato da mudança de
status — não fez parte desta entrega.

## Verificação

- `npm run test` (220 testes, 7 novos em `lib/real-estate-trends.test.ts`),
  `npx tsc --noEmit`, `npm run lint` e `npm run build` sem erros
  (`/imoveis/tendencias` aparece na build).
- **Mesma limitação de sempre**: sem Docker/Supabase local nem navegador
  autenticado pra confirmar visualmente os números e os selos de amostra
  insuficiente contra dados reais.

## Fase 4 — encerramento

Com 4.5, a Fase 4 (inteligência aplicada) do roadmap está completa: 4.1
(matching v2), 4.2 (resumo de atendimento), 4.3 (lead scoring, fallback
por regra), 4.4 (copiloto — confirmação estrutural de exclusão) e 4.5
(tendências de portfólio). Nenhum item da fase usa machine learning
propriamente dito — todos seguem a diretriz da seção 6 do roadmap ("machine
learning sem amostra: usar regras explicáveis"), com `confidence`/
`sufficientSample` sinalizando isso explicitamente em vez de fingir uma
precisão que os dados ainda não sustentam.
