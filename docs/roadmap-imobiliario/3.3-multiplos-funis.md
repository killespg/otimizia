# 3.3 — Múltiplos funis como produto

Item de Fase 3. **Não implementado nesta rodada** — bloqueado por uma
decisão deliberada tomada na 1.1, não por falta de tempo. Documentando o
porquê e o que precisa acontecer antes de retomar.

## O que o item pede

"Liberar criação, templates, permissões, relatórios e automações por funil
**sobre o schema já existente desde a 1.1**" — ou seja, o roadmap já
assume que o trabalho pesado (schema) está pronto e que este item é "só"
liberar a UI.

## Por que isso não é verdade hoje

A 1.1 (ver `docs/roadmap-imobiliario/1.1-funil-personalizavel.md`) foi
**deliberadamente aditiva**: criou `pipelines`/`pipeline_stages`, mas
nenhum ponto de leitura da aplicação foi migrado pra usar essas tabelas —
`Board.tsx`, `dashboard/page.tsx`, `devMetrics.ts`, `deals-report.ts`,
`lib/ai/tools/*`, `actions.ts`, `app/api/assistant/route.ts` (a lista
completa está em `docs/roadmap-imobiliario/0.2a-inventario-acoplamento-funil.md`)
continuam todos lendo `deals.stage`, o enum fixo de 5 valores.

"Liberar um segundo funil" de verdade significa esse segundo funil poder
ter etapas **diferentes** das 5 fixas (é o próprio motivo de existir do
item — venda, locação e captação têm processos diferentes). Isso é
impossível enquanto os ~20 pontos listados na 0.2a assumem
`novo`/`em_contato`/`negociacao`/`ganho`/`perdido` como únicas etapas
possíveis. Construir uma UI de "criar segundo funil" sem migrar esses
pontos primeiro criaria uma organização com um pipeline cujas etapas
customizadas **não apareceriam** em nenhuma tela real do produto — pior
que não ter a feature, porque pareceria que funciona.

## O que precisa acontecer antes

Migrar os pontos de leitura da 0.2a para consultar `pipeline_stages` em
vez do enum `deal_stage` fixo. Isso é um corte transversal do tamanho da
própria 1.1, com risco de regressão em telas centrais (funil, dashboard,
relatórios, assistente de IA) — motivo pelo qual a 1.1 optou por não fazer
isso junto com a criação do schema. Não é um trabalho que se encaixa como
sub-tarefa de "liberar a UI de múltiplos funis"; é um pré-requisito do
mesmo tamanho.

## Decisão

Este item fica pendente, não pulado por preferência nem por baixa
prioridade — é genuinamente bloqueado. Retomar exige, nesta ordem:
1. Migrar os pontos de 0.2a para ler de `pipeline_stages`/`pipeline_id`
   (schema já existe, é "só" trocar a fonte de leitura — mas em ~20
   lugares, com telas de produção reais).
2. Só depois disso construir a UI de criar/gerenciar múltiplos funis.

Nenhuma automação de 3.1/3.2 foi escrita assumindo múltiplos funis reais —
`pipeline_id`/`stage_key` nas regras já existem no schema (0075) e
continuam funcionando quando esse trabalho for feito, sem migração nova.
