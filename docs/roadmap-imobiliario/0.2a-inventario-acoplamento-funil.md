# 0.2a — Inventário de acoplamento do funil fixo

Item de Fase 0 do roadmap do CRM imobiliário (v6). Só inventário de leitura —
nenhuma migração ou desenho de schema aqui. Isso é trabalho do esforço G da
1.1 (funil personalizável), quando o schema `pipelines`/`pipeline_stages`
substituir o enum fixo.

## O tipo fixo

`deal_stage` é um `enum` do Postgres criado em
`supabase/migrations/0001_init.sql`:

```sql
create type deal_stage as enum ('novo', 'em_contato', 'negociacao', 'ganho', 'perdido');
```

Espelhado em TypeScript em `lib/supabase/types.ts:1-14`:

```ts
export type DealStage = "novo" | "em_contato" | "negociacao" | "ganho" | "perdido";
export const DEAL_STAGES: { key: DealStage; label: string }[] = [...];
```

Qualquer migração para múltiplos funis (schema `pipelines` + `pipeline_stages`
+ `pipeline_id` em `deals`, já decidido na seção 3 do roadmap) precisa
substituir ou conviver com esse enum e com todo ponto abaixo que trata as 5
chaves como fixas.

## Pontos que dependem das 5 chaves fixas

### Deriva dinamicamente de `DEAL_STAGES` (baixo acoplamento — não precisa mudar)

- `lib/ai/tools/validation.ts:3-5,126` — `STAGE_KEYS` e `isStage()` leem de
  `DEAL_STAGES`, não hardcodeiam as chaves. Continua funcionando se
  `DEAL_STAGES` virar dinâmico por pipeline.
- `lib/professions.ts:71` — o tipo `stages: Record<DealStage, {...}>` no
  `ProfessionPreset` é o ponto de maior acoplamento *estrutural*: força todo
  preset de profissão a ter exatamente essas 5 chaves com label customizado
  por profissão (`DEFAULT_STAGES` e os overrides em cada preset, ex.
  `real_estate_broker` linhas 218-224). Migrar para múltiplos pipelines
  provavelmente substitui isso por uma lista de etapas por pipeline
  configurável, não mais um `Record` de union type.

### Literais hardcoded `"ganho"` / `"perdido"` (filtro de negócio aberto vs. fechado)

- `lib/deals-report.ts:56,59` — soma valor ganho/perdido por período.
- `lib/deals-report.test.ts:31,35` — fixtures de teste do acima.
- `lib/ai/tools/read.ts:179` — conta negócios ganhos no mês para o copiloto.
- `lib/ai/tools/write.ts:127,141` — cria negócio com `stage: "novo"`; marca
  `closed = etapa === "ganho" || etapa === "perdido"`.
- `lib/ai/tools/definitions.ts:201` — texto da tool description do
  assistente ("'ganho' e 'perdido' fecham a venda").
- `lib/devMetrics.ts:62` — valor de negócios abertos = `stage !== "ganho" &&
  stage !== "perdido"`.
- `lib/stalled-deals.ts:15` — query Postgrest `.not("stage", "in",
  "(ganho,perdido)")` para achar negócios parados.
- `lib/whatsapp-contacts.ts:98` — cria negócio via WhatsApp com `stage:
  "novo"`.
- `app/(app)/actions.ts:321,340,368,392` — cria negócio com `stage: "novo"`;
  mesmo cálculo de `closed` em duas Server Actions distintas (duplicado, não
  compartilha helper com `lib/ai/tools/write.ts`).
- `app/(app)/actions.ts:1022-1049` — `isDealStage()` e
  `stageFromPipelineList()`: mapeia nome de lista do Trello (heurística por
  substring normalizada — "perdido"/"perda"/"lost", "fechado"/"vendido"/
  "ganho"/"won", "proposta"/"negociacao"/"visita") para uma das 5 chaves
  fixas na importação.
- `app/(app)/dashboard/page.tsx:246,253,260,275,282` — cinco comparações
  diretas para separar negócios abertos, ganhos e perdidos (mês atual e
  anterior) nos cards do dashboard.
- `app/(app)/pipeline/page.tsx:86,90` — filtra negócios abertos e ganhos
  para montar a página do funil.
- `app/(app)/pipeline/Board.tsx:591,593,607` — estilo visual do card muda
  conforme `deal.stage === "ganho"` / `"perdido"`.
- `app/(app)/pipeline/Board.tsx:849,854,870,877,880` — `STAGE_META.perdido`
  e a mesma heurística de `stageFromPipelineList` duplicada aqui para mapear
  import de board externo (mesma lógica de `actions.ts:1022-1049`, código
  repetido em vez de compartilhado).

### Lista as 5 chaves inteiras, na ordem

- `app/api/assistant/route.ts:289-291` — monta a linha de contexto do
  assistente listando as 5 chaves fixas com o label customizado por
  profissão.

## Duplicação encontrada (não é sobre múltiplos funis, mas vale registrar)

`stageFromPipelineList()` (heurística de mapeamento de nome de lista externa
→ estágio) existe **duas vezes**, quase idêntica: `app/(app)/actions.ts:1026-`
e de novo em `app/(app)/pipeline/Board.tsx` (por volta da linha 860-880). Uma
migração de schema é o momento natural para unificar isso em um único
helper, já que os dois pontos precisam saber sobre qualquer pipeline novo.

## Conclusão para a 1.1

A lista acima fecha o escopo de leitura pedido pela porta de saída da 0.2a.
O ponto de maior risco de regressão na migração não é o enum do Postgres em
si (`deal_stage`), é `lib/professions.ts` — o `Record<DealStage, ...>` por
profissão é usado para labels customizados em várias telas, e qualquer
schema novo de `pipeline_stages` precisa decidir se continua vivendo dentro
do preset de profissão ou se migra para configuração por organização,
independente da profissão.
