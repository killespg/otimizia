Item de Fase 1 (esforço M, compromisso original). Depende de 1.1 —
"configurável por etapa" pressupõe `pipeline_id`/`pipeline_stages`.

## O que foi entregue

- `supabase/migrations/0070_deal_followup_rules.sql`: tabela
  `deal_followup_rules` (org, workspace, `pipeline_id`/`stage_key`
  opcionais — `null` = coringa, dias de inatividade, `active`). RLS igual
  ao resto (todo membro da org gerencia). `tasks` ganha `source` e
  `source_rule_id` para marcar tarefas criadas automaticamente pela regra.
- `lib/followup.ts` — lógica pura: `matchRule()` escolhe a regra mais
  específica que casa com pipeline+etapa do negócio (mesmo pipeline+etapa >
  só pipeline > só etapa > coringa total); `computeFollowupCandidates()`
  decide quais negócios precisam de um follow-up agora. Testado em
  `lib/followup.test.ts` (especificidade, regra inativa, dedupe, prazo).
- `app/api/cron/followup-rules/route.ts` — aplica as regras ativas de cada
  organização contra os negócios abertos, calcula a última atividade (mesma
  fonte de `lib/stalled-deals.ts`: interação mais recente do contato, ou
  criação do negócio) e cria uma tarefa (`source = 'followup_rule'`) para
  cada negócio elegível.

## Dedupe e cooldown — simplificação deliberada

O roadmap pede "deduplicação, cooldown, pausa". Em vez de uma tabela de log
de disparo separada, o dedupe/cooldown usa o que já existe: **uma regra só
cria uma tarefa nova se o negócio não tiver nenhuma tarefa aberta com
`source = 'followup_rule'`**. Enquanto a tarefa anterior estiver aberta, ela
já é o lembrete ativo; quando o corretor conclui e o negócio esfria de
novo, a regra volta a valer. `notification_log` (usado pelo cron de
e-mail/push) não serve pra isso — o índice único por `entity_id+kind`
bloqueia um segundo disparo pro mesmo negócio para sempre, não só durante
um cooldown. "Pausa" fica coberta por `active = false` na regra.

## Por que o cron não está agendado

`vercel.json` não ganhou uma entrada nova para este cron. `deal_followup_rules`
nasce vazia para toda organização — não existe UI para criar uma regra
ainda (isso é 3.2, construtor de automações). Agendar um cron que nunca vai
encontrar regra nenhuma até existir essa UI não tem efeito, mas *decidir
quando ligar* uma automação que cria tarefas sozinha para usuários reais é
uma escolha de rollout do operador, não algo para eu ativar
silenciosamente — mesmo princípio do runbook de 0.3 (nunca big-bang).

## 1.3b — pulado nesta rodada, e por quê

1.3b (priorização avançada por pipeline/etapa) depende explicitamente de
"dados reais de uso da fila básica" (1.3a) — e a porta de saída exige um
experimento mostrando melhora sobre a ordenação básica. Como 1.3a acabou de
ser implementado nesta mesma sessão, não existe nenhum dado de uso real
ainda para calibrar pesos ou validar a melhora. Implementar 1.3b agora
seria construir "pesos configuráveis" sem nenhuma evidência de que a
ordenação atual precisa mudar — exatamente o anti-padrão que o roadmap
pede pra evitar (seção 4, portão de "mensuração": "como saberemos se
funcionou?"). Fica pendente até 1.3a rodar de verdade com uma coorte
piloto.
