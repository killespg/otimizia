# 1.3a — Central "Hoje" básica

Item de Fase 1 (esforço P/M, aposta nova, roda em paralelo — depende só de
0.1 para mensuração, não de 1.1). Confirma o que a v6 do roadmap já dizia:
"nenhum destes sinais depende do schema de etapas — só de timestamps que já
existem".

## O que foi entregue

- `lib/today.ts` — `buildTodayQueue()`, função pura que recebe listas já
  buscadas e monta uma fila única ordenada por prioridade de sinal (tarefa
  vencida → visita próxima → proposta expirando → negócio parado → negócio
  sem próxima ação), depois por data dentro de cada sinal. Testado em
  `lib/today.test.ts`.
- `lib/stalled-deals.ts` — refatorado (sem mudar comportamento do cron
  existente): a lógica de "negócio parado" virou `computeStalledDeals()`,
  reutilizável com filtro opcional de `orgId`/`ownerId`.
  `getStalledDealsByUser()` (usada por `app/api/cron/daily-email/route.ts`)
  agora é um wrapper fino sobre ela — coberto por
  `lib/stalled-deals.test.ts` pra travar que o agrupamento por usuário não
  mudou.
- `app/(app)/hoje/page.tsx` — página nova que busca, para a organização e
  usuário logado: tarefas vencidas, negócios abertos sem tarefa vinculada,
  negócios parados (`computeStalledDeals`), e — só no workspace
  `real_estate_broker` — visitas nas próximas 24h e propostas expirando em
  48h. Cada item tem motivo visível e link de ação rápida.
- Nova entrada "Hoje" no menu (`app/(app)/AppNav.tsx`), logo depois de
  "Painel", nas três variações de navegação (genérica, advocacia,
  imobiliário). **Só no menu de desktop** — decisão deliberada, ver abaixo.

## Por que "Hoje" não entrou no menu mobile

O menu mobile (`mobileItems` em `AppNav.tsx`) tem um layout fixo de 2 itens
à esquerda + botão central + itens à direita, calibrado hoje para
exatamente 4 itens por variação de navegação. Adicionar um 5º item sem
verificação visual (não havia como abrir um navegador autenticado neste
ambiente, mesma limitação já registrada em 1.2) arriscava desalinhar esse
layout sem eu conseguir confirmar. Ficou de fora do mobile de propósito —
promovê-lo lá é um ajuste pequeno e de baixo risco depois de uma checagem
visual real.

## Sinais implementados vs. o que o roadmap pede

| Sinal do roadmap | Implementado | Observação |
|---|---|---|
| Tarefa vencida | ✅ | `tasks.due_at < now`, `done = false`. |
| Visita próxima | ✅ (só imobiliário) | `real_estate_visits`, próximas 24h, `status in (requested, scheduled)`. |
| Proposta expirando | ✅ (só imobiliário) | `real_estate_offers`, próximas 48h, `status in (sent, viewed)`. |
| Inatividade registrada | ✅ | reaproveita `computeStalledDeals` (>5 dias sem interação), já existia pro cron de e-mail. |
| Ausência de próxima ação | ✅ | negócio aberto sem tarefa aberta vinculada — mesma lógica de `lib/devMetrics.ts:openDealsWithNextAction`. |
| Limite operacional | ❌, gap conhecido | esse conceito (peso/urgência configurável por etapa) só existe a partir da 1.3b, que depende do schema de etapas da 1.1. |

## Verificação

- `npm run test` — 140 testes (8 novos: `lib/today.test.ts` e
  `lib/stalled-deals.test.ts`), `npx tsc --noEmit` e `npm run lint` sem
  erros.
- `npm run build` — `/hoje` compila e aparece na lista de rotas.
- **Limitação**: sem Docker/Supabase local neste ambiente, não deu para
  abrir `/hoje` autenticado num navegador real. Antes de mergear: rodar
  local com dados de teste (tarefa vencida, negócio parado, e para
  imobiliário uma visita/proposta) e confirmar visualmente ordem, motivos e
  links.
