# 2.4 — Webhooks e API pública inicial

Item de Fase 2 (esforço M/G, evolução do compromisso). Depende de 1.1/1.2
(eventos do domínio estáveis). Decisões de produto confirmadas: escopo do
v1 é webhooks de saída **+** API de leitura (não só webhooks).

## O que já existia

`crm_domain_events` (migração 0060) já era uma fila de eventos de domínio
em Postgres, mas só alimentada para lembretes de visita (RE-3xx) — nada de
negócio (criação, mudança de etapa) emitia evento.

## O que foi entregue

- `supabase/migrations/0074_webhooks_and_api_keys.sql`:
  - Trigger em `deals` (`emit_deal_domain_event`) passa a emitir
    `deal.created` e `deal.stage_changed` em `crm_domain_events` —
    reaproveita a tabela existente em vez de criar uma fila paralela.
  - `webhook_endpoints` (URL, secret, `event_types[]`, só admin
    gerencia/lê — mesma régua de dado sensível de `organization_members`).
  - `webhook_deliveries`: uma linha por (endpoint, evento), criada
    automaticamente por trigger (`enqueue_webhook_deliveries`) quando um
    evento casa com o `event_types` de um endpoint ativo. Guarda
    `attempts`/`status`/`response_status` — os "retries e logs" que o
    roadmap pede.
  - `api_keys`: chave por organização, com `scopes` (só `read` emitido
    hoje). Só o hash fica no banco.
- `lib/api-keys.ts` / `lib/webhooks.ts`: geração de chave/secret e
  assinatura HMAC-SHA256, testados isoladamente (9 casos).
- `lib/api-auth.ts`: autentica a API pública por `Authorization: Bearer
  <chave>`, resolve a organização da chave (nunca aceita `org_id` vindo da
  query).
- `app/api/v1/deals` e `app/api/v1/contacts` (GET, paginado, só leitura).
- `app/api/cron/webhook-delivery`: processa `webhook_deliveries`
  pendentes/com falha (até 5 tentativas), assina o corpo e faz `POST` pro
  endpoint com o header `X-Otimizia-Signature`.
- `app/(app)/settings/integracoes`: página admin-only pra criar/revogar
  chaves de API e criar/ativar/desativar webhooks. O segredo (chave crua ou
  secret do webhook) só é mostrado uma vez, via **fragmento da URL**
  (`#new_key=...`) — o navegador nunca envia fragmento ao servidor, então
  não fica em log de acesso (mas ainda fica no histórico do navegador —
  trade-off de MVP, não é um cofre de segredos).

## O que fica de fora, de propósito

- **Sem retry com backoff exponencial** — o cron reprocessa no próximo
  disparo (o intervalo do cron já dá o espaçamento). Backoff de verdade é
  refinamento futuro, não bloqueante pro v1.
- **Cron não agendado em `vercel.json`** — mesma lógica do cron de
  follow-up (1.4): sem endpoint configurado por nenhuma organização ainda,
  agendar não tem efeito. Ligar o agendamento é decisão do operador quando
  o primeiro cliente piloto configurar um webhook de verdade.
- **API só de leitura** (`deals`, `contacts`) — sem escrita, sem outros
  recursos (tarefas, imóveis). O schema de `scopes` já comporta mais
  escopos quando isso for decidido, sem nova migração.
- **Sem painel de "receitas prontas"** pra Zapier/Make/n8n — a página de
  integrações documenta o header de assinatura e os endpoints, mas não tem
  um passo a passo por ferramenta. Fica pra quando houver piloto real
  usando alguma dessas.

## Verificação

- `npm run test` (181 testes, 9 novos em `lib/api-keys.test.ts` +
  `lib/webhooks.test.ts`), `npx tsc --noEmit`, `npm run lint` e
  `npm run build` sem erros — todas as rotas novas aparecem na build
  (`/api/v1/deals`, `/api/v1/contacts`, `/api/cron/webhook-delivery`,
  `/settings/integracoes`).
- `test/integration/rls.test.ts`, bloco
  `describe("webhooks e API pública (2.4)", ...)`: trigger de
  `deal.created`/`deal.stage_changed` + enfileiramento automático de
  entrega; só admin gerencia `webhook_endpoints`/`api_keys`; isolamento
  cross-org dos dois.
- **Mesma limitação de sempre**: sem Docker/Supabase local para validar as
  triggers/RLS de ponta a ponta, e sem navegador autenticado pra testar a
  página de integrações e o fluxo de criação de chave/webhook.
